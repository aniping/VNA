# 长期 Agent 协作规范

## 1. 目标与责任

本项目把 Agent 视为长期团队成员，而不是只负责单个提交的临时执行器。

- 主协调 Agent 负责产品目标、优先级、任务拆分、冲突管理、主线集成和最终验收。
- 专业 Agent 可以承接职责范围内随项目阶段变化的任务；角色是默认责任范围，不是硬隔离。
- 测试策略、双轴审核、构建复验和主线集成由主协调负责，也可以把独立只读复核临时分配给空闲专业 Agent。
- 某项工作独立、无文件冲突且有 Agent 空闲时，主协调应主动调整分工。

## 2. 固定角色与对话

显示名称可以由用户调整；对话 ID 是稳定标识，派工必须按 ID 复用。

| 通用角色 | 默认职责 | 对话 ID |
| --- | --- | --- |
| 产品与架构 Agent | 澄清用户目标，维护领域与接口契约，设计跨层纵向切片，检查是否过度设计 | `019fb71a-3fa2-7be0-af61-77606cb15402` |
| 应用与协议 Agent | 实现应用服务、命令编排、HTTP/SCPI 等外部协议和公共接口测试 | `019fb706-7b1a-7463-9219-0828161778db` |
| 平台与数据 Agent | 实现数据源、设备适配、持久化、日志、并发基础设施和跨平台能力 | `019fb706-16bc-7693-95d9-8f62808acfc7` |
| 前端与体验 Agent | 实现前端数据接入、交互、可视化、浏览器验收和用户可见文档 | `019fb709-e33c-7dd1-b688-032d48a9c426` |

除非用户明确要求创建新 Agent，主协调不得用临时子 Agent、新建任务或同目录协作 Agent 替代这四个固定对话。只有四个固定对话均无法承担且已向用户说明原因时，才可请求扩充。

## 3. 固定对话调度

1. 主协调维护按用户价值排序的任务队列，明确当前里程碑、依赖关系和验收标准。
2. 派工前读取 Codex 任务列表，按对话 ID 找到任务并核验状态、分支和工作树。
3. 向原对话发送后续任务；显示名称变化不改变职责和历史。
4. 明确任务目标、用户可见验收、基线、依赖、共享文件单一写入者、允许范围和停止条件。
5. 可并行且不修改同一文件的任务可以同时派发；存在共享热点时按集成顺序串行。
6. 派工后持续查询状态、处理阻塞、集成交付并安排下一项工作，不能只发送消息后停止协调。

## 4. Agent 实施流程

1. 在独立 worktree/分支核验基线和 `git status`；不得 reset、rebase 或覆盖其他 Agent 的修改。
2. 先明确问题、接口、成功标准和测试 seam；外部合同、状态机、数据格式、所有权和并发语义先过设计门禁。
3. 以小型纵向提交推进：设计或红测 → 最小实现 → 聚焦测试 → 完整相关测试 → 审核 → 中文提交。
4. 普通且范围清晰的实现可由主协调一次性批准文件范围、测试要求和提交权限，减少重复等待。
5. 遇到范围扩大、共享文件冲突、规模超限、破坏性操作或需求歧义时必须停止并回报。
6. 只读审核 Agent 不修改代码；审核发现由原实现 Agent 或主协调修正。
7. Agent 完成后可以等待集成，但主协调必须及时复验、集成并重新派工，不能让团队因遗漏调度长期空闲。

## 5. 长期任务看板

主协调维护 `docs/agent-task-board.md`，记录每次派工的时间、对话 ID、概要、依赖、状态、最后检查时间、阻塞、提交和下一动作。

状态只使用：

- `待开始`：任务已排队，依赖尚未满足。
- `进行中`：正在设计、编码、测试或审核。
- `受阻`：需要依赖、用户决策或外部状态变化。
- `待集成`：已有 clean 提交，等待主线合入与复验。
- `已集成`：提交已进入主线。
- `已取消`：任务被新方案替代，不再继续。

看板更新规则：

- 状态变化、发现阻塞、收到提交或完成集成后立即更新。
- 主协调活跃期间，进行中任务原则上每 5 分钟至少检查一次。
- 已知构建、长测试或审核正在运行时可以延长，但必须记录原因和最后检查时间。
- 超过一个检查周期没有说明时主动询问；连续两个周期无进展时检查进程、工作树或明确阻塞。
- 看板不替代 Git、测试结果和用户进度汇报；不得记录密钥、个人数据或大段命令输出。

## 6. 集成与连续推进

- 主协调集成前核对提交范围、顺序、测试证据和工作树状态；冲突由主协调串行处理。
- 未通过测试或验收的代码不得描述为“已完成”；已编码未集成的功能必须标记“待集成”。
- Agent 停止或等待时，必须说明是在等待依赖、审核、集成还是用户决策。
- 当前里程碑取得实质进展前，主协调应继续集成、验收、消解冲突或等待结果；不能仅报告“已安排”。

## 7. 用户进度汇报

使用通俗语言，依次说明：

1. 已经能用的功能。
2. 正在实现的用户可见功能。
3. 尚未实现且影响体验的关键缺口。
4. 各 Agent 正在负责什么，以及停止或等待的具体原因。
5. 下一步推进顺序。

不得用内部类名、测试数量或提交数量代替产品进度；技术细节只能作为补充。
