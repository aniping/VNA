# VNA 产品平台架构总纲

## 1. 文档地位

本文记录用户最初设想的产品级架构，是项目判断方向是否偏离的“北极星”，不是某一阶段的实现设计。

原始依据：

发生冲突时，适用顺序为：用户当前明确决定、本文、`docs/architecture.md` 与 `CONTEXT.md`、ADR、阶段计划、当前实现。当前代码不能反向证明架构方向正确。

## 2. 产品目标

项目目标不是制作一个浏览器仪表界面或普通 VNA 控制软件，而是构建可持续扩展的商用矢量网络分析仪核心平台，并逐步发展为测量仪器软件平台。

同一套核心应支持四种场景：

- 本地：仪器本机界面与本地控制。
- 远程：网络客户端、自动化脚本和远程仪器控制。
- 调试：命令追踪、数据追踪、故障注入、录制与回放。
- 仿真：没有硬件时完整运行；接入真实硬件后继续用于研发和测试。

## 3. 五层架构

### 3.1 呈现层

第一版使用 Vue 3 浏览器界面。呈现层负责操作体验、坐标投影和可视化，不拥有仪表业务状态，不计算 S 参数、校准结果或 Trace 格式数据。

### 3.2 交互层

负责 SCPI、命令控制、数据刷新、文件传输以及后续协议适配。所有协议应映射到统一的内部命令、查询、操作和数据合同，不能各自实现一套业务规则。

### 3.3 业务层

负责仪器模型、系统设置、激励与响应、扫频规划、资源调度、测量、校准、显示模型、项目与文件语义，并承载命令控制流和数据处理流。

### 3.4 硬件抽象层

把驱动层的芯片级原子操作组合为源、接收机、开关、触发、扫频执行等测量能力。真实硬件、仿真和回放应满足等价的业务接口。

### 3.5 驱动层

负责 FPGA、ADC、PLL、开关、时钟和通信总线等底层控制。开发期可以用软件仿真替代硬件，但上层不能依赖仿真实现细节。

## 4. 双核心流程

### 4.1 命令控制流

命令控制流决定仪器“做什么”：

```text
Vue / SCPI / Remote API
→ 协议解析
→ 统一命令与排序
→ 仪表状态和版本
→ 不可变扫频计划
→ 异步操作与资源调度
→ HAL
→ Driver
```

### 4.2 数据处理流

数据处理流决定仪器“产生什么结果”：

```text
ADC / IQ / 原始接收机数据
→ 完整原始帧
→ S 参数等 Measurement
→ 校准与数学处理
→ Trace 格式投影
→ 显示、SCPI、文件和调试消费者
```

两条流程不能靠“当前全局状态”或时间猜测关系。它们必须通过不可变的因果链汇合：

```text
Command / ConfigRevision
→ SweepPlan
→ Operation
→ Sweep / Acquisition
→ RawFrame
→ ProcessedFrame / TraceFrame
```

## 5. 不得静默改变的长期原则

1. **统一业务真值**：本地、远程、SCPI、调试和仿真共享同一业务核心。
2. **控制与数据分离**：状态修改串行化；完成数据不可变并可并行处理。
3. **配置按安全边界生效**：在途 Sweep 使用创建时的不可变快照；新配置不得污染旧帧。
4. **完整因果追踪**：命令、状态版本、计划、操作、Sweep、采集和帧必须可关联。
5. **Measurement、Trace、Window 分离**：Measurement 表示测什么，Trace 表示怎样显示，Window 只负责布局。
6. **一次采集复用**：同一 Channel 的兼容 Measurement 和 Trace 共享一次原始采集、校准结果与中间数据，不得按 Trace 重复扫频。
7. **多端口能力驱动**：端口数、源状态和接收机能力由 Capability 与 Sweep Plan 表达，不复制多套业务链路。
8. **硬件可替换**：Simulation、Replay 和真实 Hardware 在 HAL seam 上等价；正式仿真输出原始接收机数据，不能只伪造最终曲线。
9. **协议与前端保持轻薄**：协议不实现业务状态机，前端不进行 VNA 领域计算。
10. **不同消费者使用不同可靠性策略**：实时显示允许 latest-only；单次扫频、校准、SCPI 数据查询和录制不得静默丢失。
11. **校准和数据版本化**：CalSet、完成帧和项目格式必须可追溯、可迁移；已完成对象不可就地改写。
12. **跨平台是正式合同**：Windows/MinGW 与 Linux/GCC 均是一等目标，平台差异收敛在适配器中。
13. **纵向切片交付**：每个阶段应形成真实公共接口或用户可见闭环，避免长期堆积无法运行的基础设施。

## 6. 当前阶段与总纲的关系

当前“持续采集数据动脉、默认 S21、实时显示”是优先级最高的阶段性纵向切片。它用于验证双核心流程、仿真替换、帧因果链和浏览器呈现，但不等于完整产品架构。

后续仍需在相同总纲下扩展 Trigger、Sweep Planner、校准、Marker、文件、SCPI、Record/Replay、真实硬件、多通道和高级测量。

## 7. 可以演进的实现选择

以下内容只要不破坏上述长期原则，可以按证据调整：

- 具体编程库、日志库、网络库和内部容器。
- 类名、文件布局、私有 helper、线程池和队列实现。
- REST、WebSocket、二进制协议的具体编码和版本。
- SVG、Canvas 或 WebGL 绘图技术。
- SQLite、HDF5 或其他持久化实现。
- 模块是否在未来拆为独立进程，以及进程间传输方式。
- 仿真模型的具体公式、性能参数和容量上限。

这些选择不得被写成顶层产品目标，也不能因为当前实现方便而倒置依赖关系。

## 8. 架构变更确认流程

需要改变五层职责、四种场景、双核心流程、业务真值所有权、数据因果链、硬件替换能力或跨平台目标时，必须：

1. 明确指出与本文哪一项不同。
2. 说明原因、用户可见影响、兼容性、风险和替代方案。
3. 在编码前取得用户明确确认。
4. 新增或更新 ADR，并同步修改本文。
5. 在实现完成后再次检查实际结果是否符合获批的新决定。

用户可以调整最初设想；本文的作用是防止未经确认的静默漂移，而不是阻止合理演进。

## 9. 大需求完成后的架构回看

涉及两个以上层级、公共合同、状态机、数据链、所有权、部署方式或用户默认流程的需求，在宣布完成前必须回答：

- 用户可见目标是否形成真实端到端闭环？
- 改动位于正确层级，还是把业务规则泄漏到了协议、前端或驱动？
- 命令控制流和数据处理流的职责、汇合点及因果关系是否仍清楚？
- 是否产生第二套业务真值、第二个采集所有者或按 Trace 重复采集？
- 状态版本、计划、操作、Sweep 和帧是否仍能完整追踪？
- Simulation 与真实 Hardware 的替换 seam 是否仍成立？
- Measurement、Trace、Window、校准和文件语义是否仍分离？
- Windows 与 Linux 合同是否仍成立？
- 相关公共接口测试、完整测试以及必要的发布版实机验收是否通过？
- 是否偏离本文；若偏离，是否已有用户确认和 ADR 记录？
